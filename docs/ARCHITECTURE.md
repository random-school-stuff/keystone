# Architecture

Keystone is a browser-side proxy engine plus a small Node server. This document explains the two deployment targets, what each piece does, how a request moves through the system, and the constraints that are easy to break.

---

## 1. Two deployment targets

The same Ultraviolet bundle runs in two places, wired up by two different pages. The Pages page can additionally switch to Scramjet or to the engine written for this repository; the Node app cannot, and drives Ultraviolet only.

| | Static site | Node app |
|---|---|---|
| Page | `docs/index.html`, one self-contained file | `public/index.html`, plus `styles.css`, `app.js`, `register-sw.js`, `search.js` |
| Host | GitHub Pages, served from `/docs` on `main` | Any server with Node 24, or Docker |
| Engine files | `docs/uv/`, `docs/scram/`, `docs/keystone/`, `docs/baremux/`, `docs/epoxy/`, `docs/libcurl/`, committed to git | `public/uv/`, `public/baremux/`, `public/epoxy/`, generated by `npm run build` |
| Engines available | Scramjet, Ultraviolet, or Keystone, chosen in settings | Ultraviolet only |
| Proxy backend | None. Points at a Wisp endpoint hosted elsewhere | `src/index.js`, mounted at `/wisp/` on the same origin |
| Default Wisp endpoint | `DEFAULT_WISP` in the page: currently the public demo `wss://wisp.mercurywork.shop/` | Same origin: `wss://<host>/wisp/` or `ws://<host>/wisp/` |

GitHub Pages is static-only. It serves files and nothing else, so the Pages deployment must reach a Wisp server that is running somewhere else. The Node app is the thing that can be that server, and it also serves its own page, so a single deployment can be self-contained.

Both targets use the same Ultraviolet, bare-mux and Epoxy versions. They are not otherwise identical: the Pages site carries two more engines — vendored Scramjet and the hand-written Keystone engine — and lets the visitor pick between all three, while the Node app still drives Ultraviolet only. The page wrapper, the engine selection, and the endpoint resolution are what differ.

## 2. Components

| Component | Package / file | Runs where | Role |
|-----------|----------------|-----------|------|
| Node server | `src/index.js` | Server | Serves static files, mounts the Wisp upgrade endpoint, exposes `/healthz` |
| Wisp server | `@mercuryworkshop/wisp-js` 0.5.1 | Server | Accepts WebSocket streams and makes the real outbound connections |
| Scramjet | `@mercuryworkshop/scramjet` 1.1.0 | Browser service worker | Default engine. Successor to Ultraviolet, actively maintained, handles the most sites and supports CAPTCHA pages |
| Ultraviolet | `@titaniumnetwork-dev/ultraviolet` 3.2.10 | Browser service worker | Legacy engine. Upstream is deprecated ("Succeeded by Scramjet") and unmaintained; kept because it still works and is the only engine the Node app ships |
| Keystone engine | `docs/keystone/sw.js`, `docs/keystone/client.js`, `docs/keystone/keystone.config.js` | Browser service worker + page | Hand-written engine for this repo. Document-level HTML/CSS rewriting only; see section 6 |
| bare-mux | `@mercuryworkshop/bare-mux` 2.1.9 | Browser page + worker | Transport abstraction; loads and switches transport modules |
| Epoxy | `@mercuryworkshop/epoxy-transport` 2.1.29 | Browser worker | Encrypted transport that speaks Wisp over a WebSocket. Default. |
| Libcurl | `@mercuryworkshop/libcurl-transport` 2.0.6, wrapped by `docs/transports/libcurl.mjs` | Browser worker | Alternative encrypted transport, selectable in settings |
| Caddy | `caddy:2-alpine` | Server (container) | TLS termination, HTTP/2, reverse proxy, WebSocket passthrough |
| Express | `express` 5.x | Server | Static file serving and routing |

No engine touches the network directly. Each one hands work to a transport, and the transport hands it to Wisp. That split is why the page can point at a Wisp server on another host with no server-side changes, and why the engine and the transport are separate choices in settings (5.3).

## 3. Load order

This is the one thing most likely to be reintroduced by a refactor, so it is stated explicitly.

Only one engine script is in the markup:

```html
<script src="baremux/index.js" defer></script>
```

`bare-mux` has to exist before any engine bundle runs, and it is the one piece every engine shares, so it loads unconditionally. The engine bundles themselves — `uv/uv.bundle.js` plus `uv/uv.config.js`, `scram/scramjet.all.js`, or `keystone/keystone.config.js` — are injected by the app script on the first launch, through `ensureEngine()`. Loading all three up front breaks the page outright; 5.3 explains why.

`defer` scripts run after parsing, in document order. The application code is an inline `<script>` at the end of `<body>`, and inline scripts are **not** deferred — they run as soon as the parser reaches them, which is *before* the deferred `baremux/index.js` executes.

An earlier version ran `init()` immediately. At that moment `BareMux` and `__uv$config` were still undefined, the constructor threw, and the whole script died. Nothing on the page worked: no settings, no theme toggle, no proxying. The page rendered but was inert.

The fix is to wait for the event that fires after deferred scripts have run:

```js
if (document.readyState === "loading") {
	document.addEventListener("DOMContentLoaded", init, { once: true });
} else {
	init();
}
```

The `readyState` check covers the case where the script is injected after the document has already finished parsing.

The guard is still required now that the engine bundles are lazy. `init()` constructs `BareMux.BareMuxConnection` at the top, before anything else happens, and that constructor needs the deferred `baremux/index.js`. Removing the guard because "the engines load on demand anyway" reintroduces exactly the failure described above.

The Node app page does not need this: `app.js` is itself loaded with `defer`, and deferred scripts execute in document order after the engine scripts. Any change that makes `app.js` load earlier than `baremux/index.js` reintroduces the failure.

## 4. Config path derivation

`docs/uv/uv.config.js` has to work in two contexts and at two different base paths.

- In the page, it is loaded with `<script src="uv/uv.config.js">`.
- In the service worker, it is loaded with `importScripts("uv.config.js")`.

A GitHub Pages project site lives under a subpath such as `/keystone/`, while the Node app lives at the root. Hard-coding either one breaks the other. The file derives the base from whichever context is loading it:

```js
var source =
	(typeof document !== "undefined" &&
		document.currentScript &&
		document.currentScript.src) ||
	(typeof self !== "undefined" && self.location && self.location.href) ||
	"";

// Path only, no origin: e.g. /keystone/uv/
var base = new URL(source, self.location.href).pathname;
base = base.slice(0, base.lastIndexOf("/") + 1);
```

`document.currentScript.src` gives the full URL of the config file when the page loads it; in the service worker there is no `document`, so `self.location.href` is used instead. Taking `.pathname` and slicing back to the last `/` yields the directory, with no origin and no query string.

**The constraint that matters:** Ultraviolet matches incoming requests with `location.origin + config.prefix`. The prefix is concatenated onto the origin, so it must be a root-relative **path**, never a full URL. A prefix of `https://example.com/uv/service/` would produce `https://example.comhttps://example.com/uv/service/` and every proxied request would miss. Every value in the config is built the same way:

```js
self.__uv$config = {
	prefix: base + "service/",
	encodeUrl: Ultraviolet.codec.xor.encode,
	decodeUrl: Ultraviolet.codec.xor.decode,
	handler: base + "uv.handler.js",
	client: base + "uv.client.js",
	bundle: base + "uv.bundle.js",
	config: base + "uv.config.js",
	sw: base + "uv.sw.js",
};
```

The Node app uses the simpler fixed form in `public/uv/uv.config.js` (`prefix: "/uv/service/"`), because it is always served from the domain root.

`docs/keystone/keystone.config.js` derives its base with the same code and for the same reason, and defines `prefix: base + "g/"` on `self.__keystone$config`. Scramjet's prefix is computed in the page instead (`new URL("scram/service/", location.href).pathname`), because its config lives in IndexedDB rather than in a script the worker imports, but the constraint is identical: root-relative path, no origin.

### Service worker scope

The Pages page registers the worker with a relative URL and no explicit scope. The URL comes from the `PROXY_ENGINES` table, so the same code registers whichever engine is selected:

```js
var swUrl = new URL(spec.sw, location.href).href;
navigator.serviceWorker.register(swUrl);
```

With no `scope` argument the worker's scope is its own directory, `…/uv/`, `…/scram/` or `…/keystone/`. That is intentional: each engine's proxied path sits inside its own directory, so a worker registered at a wider scope would intercept requests it has no reason to see — and, with three engines installed, would also see the other engines' traffic.

`registerSW()` waits for the registration to become `active` rather than relying on `controllerchange`, because the page does not control the frame the engine drives. A 5 second ceiling keeps a stuck activation from blocking a launch forever.

## 5. Request flow

### 5.1 First page load

```text
Browser --GET /keystone/--> GitHub Pages --> docs/index.html
Browser --GET /         --> Caddy --> Express static --> public/index.html
```

The page loads `baremux/index.js`, `init()` runs on `DOMContentLoaded`, and the selected engine's bundle is injected on the first launch. See 5.3.

### 5.2 Selecting a transport

The page creates a `BareMuxConnection` against `baremux/worker.js`, resolved relative to the page so it works under a subpath:

```js
var connection = new BareMux.BareMuxConnection(
	new URL("baremux/worker.js", location.href).href
);
```

On launch it installs the transport the user picked in settings and tells it where the Wisp server is. `getTransportSpec()` returns the module URL plus the constructor options, because the two transports disagree on the option name:

```js
// Epoxy
{ url: new URL("epoxy/index.mjs", location.href).href, options: [{ wisp: wispUrl }] }

// Libcurl
{ url: new URL("transports/libcurl.mjs", location.href).href, options: [{ websocket: wispUrl }] }
```

The result is cached in `activeWisp` and `activeTransport`. If the same transport is already installed and the Wisp URL has not changed, it is reused rather than reinstalled.

#### Why libcurl goes through an adapter

`bare-mux` 2.1.9 hands a transport a plain object of request headers:

```js
let o = s instanceof Headers ? Object.fromEntries(s) : s;
```

`LibcurlClient.request()` in the latest published libcurl-transport (2.0.6) iterates its `headers` argument instead:

```js
for (let [key, value] of headers) {
```

A plain object is not iterable, so every request threw `TypeError: headers is not iterable` and Ultraviolet turned it into a 500 page. There is no newer release to wait for, so `docs/transports/libcurl.mjs` subclasses `LibcurlClient` and converts the header shape before delegating. It is the only hand-written module under `docs/transports/`, and `scripts/build-site.mjs` does not touch it.

`bare-mux` loads transports with `await import(url)` and reads the **default** export, so the adapter must export a class as `default`. A named export alone is not enough.

### 5.3 Selecting an engine

The settings drawer has two dropdowns that look similar and have nothing to do with each other:

| Dropdown | Storage key | Chooses |
|---|---|---|
| Engine | `keystone.proxyEngine` | Which proxy engine fetches, rewrites and serves pages |
| Transport | `keystone.transport` | How that engine's requests reach the Wisp server |

They compose freely: any engine works over either transport.

| Engine | Role | Service worker | Prefix |
|---|---|---|---|
| Scramjet 1.1.0 | Default | `docs/scram/sw.js` | `/scram/service/` |
| Ultraviolet 3.2.10 | Legacy | `docs/uv/sw.js` | `/uv/service/` |
| Keystone | Written for this repo | `docs/keystone/sw.js` | `/keystone/g/` |

`getProxyEngine()` reads the stored value and falls back to `DEFAULT_PROXY_ENGINE` (`"scramjet"`) when it is not a key of `PROXY_ENGINES`, so a stale or hand-edited `localStorage` entry cannot leave the page with no engine at all. The same table supplies the service worker URL and the hint text under the dropdown, which `syncEngineHint()` rewrites whenever the selection changes. Resetting settings writes an empty key and restores `scramjet`.

Scramjet is the default because it is the only one of the three that is both complete and maintained: it is the designated successor to Ultraviolet, covers the most sites, and handles CAPTCHA pages. Ultraviolet stays selectable because it still works and because the Node app is built around it, but its upstream is marked deprecated — "Succeeded by Scramjet" — and receives no fixes. The Keystone engine is not in the same class as either, and section 6 says so plainly.

#### Why the engine bundles load lazily

`ENGINE_SCRIPTS` maps each engine to the scripts it needs, and `ensureEngine(engine)` injects them in order, awaiting each, the first time that engine is used:

```js
var ENGINE_SCRIPTS = {
	ultraviolet: ["uv/uv.bundle.js", "uv/uv.config.js"],
	scramjet: ["scram/scramjet.all.js"],
	keystone: ["keystone/keystone.config.js"],
};
```

Order matters inside a bundle — `uv.config.js` reads `Ultraviolet`, so it has to run after `uv.bundle.js` — which is why the injection is a promise chain rather than a handful of parallel `<script>` tags.

Two reasons the bundles are not all present from the start:

1. **They conflict.** Every engine bundle embeds its own copy of `bare-mux`. With more than one loaded, the copies compete for the same `BroadcastChannel("bare-mux")` and the service worker intermittently fails every request with `there are no bare clients`. This is not an ordering problem that can be scheduled away; the copies simply must not coexist.
2. **They are large.** Ultraviolet's bundle is around 1 MB; Scramjet adds roughly 180 KB of script plus a 537 KB WebAssembly module. Loading all of it on every visit in order to use one engine is waste.

The load promise is cached per engine in `engineLoaded`, so later launches reuse it. A failed load deletes its own cache entry before rethrowing: without that, a retry would resolve instantly against nothing and the failure would look like a silent no-op.

Launch order is fixed, and each step depends on the previous one: register the engine's service worker, load the engine's scripts, install or reuse the transport, then open the frame.

#### The Scramjet frame model

Ultraviolet and Keystone are driven by assigning `frame.src = engineUrl(engine, target)`. Scramjet is not. It has to attach its client to the iframe before navigation, so it hands back a frame object instead.

`getScramController()` builds a `ScramjetController` once and keeps it, because `init()` writes configuration into IndexedDB and must not run on every launch. `createFrame(iframe)` returns a `ScramjetFrame` with `go(url)`, `reload()`, and a `urlchange` event. The page keeps that object in `scramFrame`, uses `urlchange` to update the address bar, and calls `scramFrame.reload()` for the reload button rather than reaching into `contentWindow`. The handle is dropped when the browser is closed or the engine changes: a frame object belongs to one navigation session, and the next launch attaches a fresh one.

`engineUrl()` and `decodeEngineUrl()` exist for the same reason. Each engine encodes target URLs differently — Scramjet's own codec, Ultraviolet's XOR codec, Keystone's URL-safe base64 — so the address bar decodes by trying each in turn and keeping the first that matches.

#### Scramjet config, and the IndexedDB race

Scramjet is the one engine whose configuration does not travel through a script global. `ScramjetController.init()` writes it into an IndexedDB database named `$scramjet`, and the service worker reads it back with `loadConfig()` on every fetch. That indirection is why `docs/scram/sw.js` is not the upstream example verbatim.

`ScramjetServiceWorker`'s constructor opens `$scramjet` at version 1 with **no** upgrade callback. `ScramjetController.openIDB()` opens the same database **with** an upgrade callback that creates the object stores. IndexedDB only runs an upgrade when the version increases, so whichever side opens the database first decides its shape: if the worker wins the race it creates an empty version 1 database, the controller's upgrade never runs, and every request fails with

```text
NotFoundError: One of the specified object stores was not found.
```

The page normally gets there first because it initialises the controller before launching, but that is not guaranteed — a hard reload can invert the order. `docs/scram/sw.js` removes the race by creating the five stores (`config`, `cookies`, `redirectTrackers`, `referrerPolicies`, `publicSuffixList`) itself in an `onupgradeneeded` handler, and only constructing `ScramjetServiceWorker` after that promise resolves. Its fetch listener also ignores anything outside `self.registration.scope`, because `route()` reads `config.prefix`, which is undefined until `loadConfig()` has run.

Scramjet is also the reason this project does not depend on cross-origin isolation. It applies COOP/COEP headers conditionally (`crossOriginIsolated && …`) rather than requiring them, and it only needs `SharedArrayBuffer` for synchronous XHR, which is behind a feature flag. That matters here because GitHub Pages cannot send custom headers at all.

### 5.4 Navigating to a proxied URL

With Ultraviolet selected, a launch looks like this. The shape is the same for the other two engines; only the prefix and the rewrite rules change.

```text
Browser
  |  GET <base>/uv/service/<encoded target URL>
  v
Service worker (.../uv/sw.js)
  |  decode target, build request through the transport
  v
bare-mux worker  ->  Epoxy  ->  WebSocket to the Wisp endpoint
  v
Wisp server
  |  outbound HTTPS
  v
Target site
  |  response
  v
Wisp  ->  Epoxy  ->  service worker
  |  rewrite HTML/CSS/JS so links and assets stay under <base>/uv/service/
  v
iframe in the page
```

The proxied page renders inside an iframe (`#uv-frame`). Ultraviolet rewrites absolute URLs, injects its client script, and redirects navigations back through the service worker, so following a link inside the frame stays proxied. The page decodes the iframe URL back to a plain address for the address bar.

### 5.5 The Wisp upgrade path

The Node server attaches a raw `upgrade` listener to its HTTP server:

```js
server.on("upgrade", (req, socket, head) => {
	// ...
	if (pathname === "/wisp/" || pathname === "/wisp") {
		wisp.routeRequest(req, socket, head);
		return;
	}
	socket.destroy();
});
```

Only `/wisp/` (and `/wisp`) reaches Wisp. Any other upgrade path is destroyed immediately, so nothing else on the host can be reached through a stray WebSocket. Caddy forwards the upgrade because `reverse_proxy` handles WebSocket transparently; no special directive is needed.

On GitHub Pages there is no server, so this path does not exist there. The browser connects directly to whatever host `DEFAULT_WISP` points at.

## 6. The Keystone engine

`docs/keystone/` is a proxy engine written for this repository, not a vendored package. It exists because the other two are large third-party bundles and one of them is abandoned, and because a small engine that does the simple half of the job is easier to reason about when something breaks.

**What it is not.** Keystone rewrites documents, not programs. There is no JavaScript emulation, no `Function` rewriting, no `import` interception, no worker support, no `eval` handling. A site that builds its content in the browser will not render. That is the design, not a bug waiting to be fixed, and the settings hint says so: "It handles static pages only; use Scramjet for anything that relies on JavaScript."

### 6.1 Configuration

`docs/keystone/keystone.config.js` is shared by the page and the worker, like `uv.config.js`. The page gets it injected by `ensureEngine()`; the worker loads it with `importScripts("keystone.config.js")`. It defines one global:

```js
self.__keystone$config = {
	prefix: base + "g/",
	client: base + "client.js",
	encode: encode,
	decode: decode,
};
```

`base` is derived from the script's own URL exactly as described in section 4, so the engine works at a domain root and under a GitHub Pages subpath such as `/keystone/`. `prefix` is a root-relative **path**, never a full URL, for the same reason as every other engine: the worker matches requests with `location.origin + prefix`.

`encode` and `decode` are URL-safe base64: `+` and `/` become `-` and `_`, and `=` padding is stripped. A proxied address therefore stays a single readable path segment with no percent-encoding:

```text
/keystone/g/aHR0cHM6Ly9lbi53aWtpcGVkaWEub3JnL3dpa2kvUHJveHlfc2VydmVy
```

### 6.2 What the worker rewrites

`docs/keystone/sw.js` handles every request under `location.origin + prefix`. It decodes the target from the path, rejects anything that is not `http:` or `https:`, fetches it through a `BareMux.BareClient`, and rewrites the response. For HTML:

- URL-bearing attributes: `src`, `href`, `action`, `poster`, `formaction`, `data-src`, `data-href`, `cite`, `background`, `longdesc`
- `srcset`, candidate by candidate, preserving the width and density descriptors
- `url(...)` and `@import "..."` in `<style>` blocks, in `style=""` attributes, and in standalone CSS responses — one function handles all three, so there is no separate CSS path to keep in sync
- a `client.js` tag, injected immediately after the opening `<head>` tag (or at the top of the document when there is no head) so the runtime shim is in place before any page script runs
- redirect `Location` headers, turned into proxied URLs so the browser never leaves this origin

Everything else — images, fonts, scripts, JSON, media — is passed through untouched. That is deliberate: the worker does not claim to rewrite what it cannot.

References resolve against the response URL, so relative links work. Fragments and non-HTTP schemes (`javascript:`, `mailto:`, `tel:`, `data:`, `blob:`, `about:`, `file:`, `ws:`, `wss:`) are left alone.

### 6.3 What it strips

| Removed | Why |
|---|---|
| `integrity` attributes | The hash covers the original bytes. Once the URL is rewritten the browser fetches a different body, the hash no longer matches, and the browser drops the asset instead of loading it. |
| `<meta http-equiv="content-security-policy">` | The target's policy would block the injected `client.js` and every rewritten subresource |
| `content-security-policy`, `content-security-policy-report-only` | Same reason, header form |
| `content-encoding`, `content-length` | The body is decoded and rewritten, so the originals are wrong and would truncate the response |
| `x-frame-options`, `cross-origin-opener-policy`, `cross-origin-embedder-policy`, `cross-origin-resource-policy` | These stop the page rendering in a frame on this origin |
| `strict-transport-security` | Meaningless on the proxying origin, and would pin HTTPS for this host |
| `set-cookie` | The cookie belongs to the target origin; forwarding it would write the target's session into this origin's cookie jar |

Request headers are normalized too: `host`, `origin`, `referer`, `sec-fetch-site` and `accept-encoding` are dropped, and `referer` is set to the target's origin so sites that check it behave normally. The fetch uses `redirect: "manual"` so the worker can see and rewrite `Location` itself instead of having the redirect followed invisibly.

### 6.4 The runtime shim

`docs/keystone/client.js` patches the URLs that only exist at runtime, which no amount of document rewriting can see:

- `fetch`, including a `Request` argument
- `XMLHttpRequest.prototype.open`
- `history.pushState` and `replaceState`, so a script that pushes a path does not navigate the frame off-origin
- `window.open`
- a `MutationObserver` over the whole document, which fixes `src`, `href`, `poster` and `action` on elements added after load

It is best effort by design, and the file says as much. Anything that builds a URL and hands it to an API not patched here leaves the proxy.

### 6.5 Three bugs worth not reintroducing

Each of these was found by testing against real sites, and each is a small-looking mistake with a silent failure mode.

**1. HTML entities in query strings.** Attribute values arrive HTML-escaped, so `?a=1&amp;b=2` reaches the rewrite regex as literal text. Resolving that with `new URL()` keeps `amp;` as part of the parameter name, corrupting every query string on every rewritten page — usually invisible until a stylesheet or image with a cache-busting parameter fails. `decodeAttr()` decodes on the way in and `encodeAttr()` re-encodes on the way out.

**2. Double-proxying.** An absolute URL that already pointed at a proxied path on this origin was wrapped a second time. The target then became a `127.0.0.1` address the Wisp server refuses to reach, so the asset failed with an error naming neither the asset nor the cause. Both the worker (`rewriteRef`) and the shim (`rewrite`) now skip references already under their own prefix.

**3. A stale `BareClient`.** A `BareClient` holds one port to the bare-mux worker. After a reload recreates that worker, a cached client keeps talking to the dead instance and every request comes back `there are no bare clients`. The worker now builds a client per request — cheap, and always resolves the current worker.

### 6.6 Measured behaviour

Through the shared demo Wisp endpoint:

| Site | Keystone | Scramjet | Ultraviolet |
|---|---|---|---|
| `en.wikipedia.org` | Renders, styled | Renders | Renders |
| GitHub | Renders | Renders | Renders |
| YouTube | Does not render | Renders | Renders |
| Google search | Does not render | Renders | Renders |
| Reddit | Bot wall | Bot wall | Bot wall |

On the Wikipedia article, Keystone applied 12 stylesheets with 0 broken images, and the computed body background was `rgb(248, 249, 250)` with a `sans-serif` font — genuinely styled, not merely readable markup. YouTube and Google are JavaScript applications and fall outside the engine's design. Reddit returns a bot wall on all three engines, which is the site's policy against shared datacenter IPs, not a defect in any of them.

### 6.7 Where it stands

Keystone is selectable, honest about its limits, and not a replacement for Scramjet. It is useful for static documentation, wikis and article sites, and it is small enough to read in one sitting when something goes wrong. For anything else, use the default.

## 7. Wisp endpoint resolution

The Pages page resolves its endpoint in four steps, first match wins:

```js
function getWispUrl() {
	var fromQuery = new URLSearchParams(location.search).get("wisp");
	if (fromQuery) return normalizeWisp(fromQuery);

	var saved = read(STORAGE.wisp, "");
	if (saved) return normalizeWisp(saved);

	if (DEFAULT_WISP) return normalizeWisp(DEFAULT_WISP);

	if (location.hostname === "localhost" || location.hostname === "127.0.0.1") {
		var scheme = location.protocol === "https:" ? "wss" : "ws";
		return scheme + "://" + location.host + "/wisp/";
	}

	return "";
}
```

1. `?wisp=` in the query string. Useful for trying a server without saving anything.
2. The saved value in `localStorage` under `keystone.wisp`, written by the settings drawer.
3. `DEFAULT_WISP` in the page. The shipped value is `wss://wisp.mercurywork.shop/`, a public demo server shared with other people and intended for testing.
4. The same-origin `/wisp/`, but only on `localhost` or `127.0.0.1`, where a local Node app is likely to be running.

If all four produce nothing, the endpoint is empty and launching shows an inline error with an "Open settings" action rather than failing silently.

### 7.1 Presets in the settings drawer

The drawer's **Server** dropdown offers a small set of presets instead of asking people to type a URL:

| Preset | Endpoint | Offered when |
|--------|----------|--------------|
| Mist Services | `wss://wisp.mercurywork.shop/` | Always. This is the same value as `DEFAULT_WISP`. |
| This site's own server | same-origin `/wisp/` | Only where a Wisp server could actually run |
| Custom server… | whatever is typed | Always |

Saving a preset writes an empty `keystone.wisp`, so `DEFAULT_WISP` keeps governing and the preset stays correct if the default ever changes.

The self-hosted preset is added at runtime by `addLocalPreset()`, not in the markup. GitHub Pages, Netlify, Vercel, Cloudflare Pages and Surge serve files only, so a same-origin `/wisp/` can never exist there; listing the option would give people a choice that is guaranteed to fail. The check is a hostname suffix match:

```js
function canRunOwnServer() {
	return !/(^|\.)(github\.io|pages\.dev|netlify\.app|vercel\.app|surge\.sh)$/i.test(
		location.hostname
	);
}
```

The **Transport** dropdown selects between Epoxy and Libcurl, covered in 5.2. Epoxy is the default because it is the most reliable: Libcurl installs and proxies correctly, but some sites render slowly or not at all through it, so it is labelled experimental rather than presented as an equal choice.

The **Engine** dropdown sits directly above it, at the top of the Proxy section, and selects the proxy engine rather than the transport — covered in 5.3. Its hint text is replaced on every change by `syncEngineHint()`, because the three engines have genuinely different limits and the dropdown labels alone ("legacy", "basic") do not explain them.

### 7.2 Normalization

`normalizeWisp()` accepts loose input:

- a bare host, `host`, becomes `wss://host/wisp/`
- `http://` is rewritten to `ws://`, `https://` to `wss://`
- an empty path, `/` or `""`, becomes `/wisp/`

Invalid input is returned unchanged; the connection attempt then fails and is reported.

### 7.3 Mixed content

```js
function isSecureForPage(wispUrl) {
	return location.protocol !== "https:" || wispUrl.indexOf("wss://") === 0;
}
```

An HTTPS page may only use a `wss://` endpoint. A `ws://` endpoint is rejected in two places: when saving in the settings drawer, and again at launch. Both cases show a message and offer the settings drawer. This check exists because the browser would otherwise block the socket with a mixed-content error that is hard to interpret. The Pages site is always HTTPS, so it is always subject to this rule.

### 7.4 Testing and status

The drawer's Test button opens a real `WebSocket` to the normalized address and resolves on `onopen` or `onerror`, with an 8 second timeout. It reports the result inline.

The pill in the top bar reflects state through `data-state`:

| State | Set by | Meaning |
|---|---|---|
| `checking` | launch | A launch is in progress |
| `ready` | `refreshConn()` | An endpoint is configured and allowed on this page |
| `ok` | launch | The transport was installed and the session opened |
| `fail` | launch, or `refreshConn()` when the scheme is wrong | Launch failed, or an HTTPS page has a `ws://` endpoint |
| `unset` | `refreshConn()` | No endpoint resolved |

## 8. Build outputs

There are two vendor scripts and they are not interchangeable.

`scripts/build.mjs` copies files out of `node_modules` into `public/`:

| Source package | Destination | Files |
|----------------|-------------|-------|
| `@titaniumnetwork-dev/ultraviolet` (`uvPath`) | `public/uv/` | `sw.js`, `uv.bundle.js`, `uv.client.js`, `uv.handler.js`, `uv.sw.js` |
| `@mercuryworkshop/bare-mux` (`baremuxPath`) | `public/baremux/` | `worker.js`, `index.js`, `index.mjs` |
| `@mercuryworkshop/epoxy-transport` (`epoxyPath`) | `public/epoxy/` | `index.mjs` |

`scripts/build-site.mjs` does the same into `docs/`, with these differences: bare-mux gets only `index.js` and `worker.js`, it also vendors the libcurl transport and Scramjet, and the hand-written configs are left alone.

| Source package | Destination | Files |
|----------------|-------------|-------|
| `@titaniumnetwork-dev/ultraviolet` (`uvPath`) | `docs/uv/` | `sw.js`, `uv.bundle.js`, `uv.client.js`, `uv.handler.js`, `uv.sw.js` |
| `@mercuryworkshop/bare-mux` (`baremuxPath`) | `docs/baremux/` | `index.js`, `worker.js` only |
| `@mercuryworkshop/epoxy-transport` (`epoxyPath`) | `docs/epoxy/` | `index.mjs` |
| `@mercuryworkshop/libcurl-transport` (`dist`) | `docs/libcurl/` | `index.mjs` |
| `@mercuryworkshop/scramjet` (`scramjetPath`) | `docs/scram/` | `scramjet.all.js`, `scramjet.sync.js`, `scramjet.wasm.wasm` |

Scramjet ships three files and all three are needed: `scramjet.all.js` is the page and worker bundle the page injects, `scramjet.sync.js` is the synchronous worker Scramjet starts for its own XHR path, and `scramjet.wasm.wasm` is the rewriter. The controller is told where they live through its `files` option, so the paths must match this layout.

libcurl's WebAssembly module is embedded inside `index.mjs`, so no `.wasm` file is served. An earlier version of the script also copied `libcurl.wasm`; that file was never requested and has been removed.

These files under `docs/` are hand written and are not managed by either script:

| File | Why it is not vendored |
|---|---|
| `docs/uv/uv.config.js` | Derives its own base path (section 4) |
| `docs/scram/sw.js` | Upstream worker plus the IndexedDB schema repair described in 5.3 |
| `docs/keystone/sw.js`, `client.js`, `keystone.config.js` | The engine itself; see section 6 |
| `docs/transports/libcurl.mjs` | Header-shape adapter for bare-mux 2.1.9 (5.2) |

Editing any of them is safe from a rebuild; forgetting to commit one is not, because Pages serves whatever is in git.

Both scripts resolve the source directories from the packages themselves rather than hard-coding paths, so an upstream layout change surfaces as a build error instead of a silently stale file.

### 8.1 Why `public/` is generated

`public/` is derived output, excluded by `.gitignore`:

```text
public/uv/sw.js
public/uv/uv.bundle.js
public/uv/uv.client.js
public/uv/uv.handler.js
public/uv/uv.sw.js
public/baremux/
public/epoxy/
```

The reasons:

1. **One source of truth.** `package.json` and `package-lock.json` pin the versions. Copied bundles in git can drift from the installed packages, and a reader cannot tell which is authoritative.
2. **No manual upgrades.** Bumping Ultraviolet is `npm install` plus a rebuild.
3. **Smaller history.** These are compiled bundles, some hundreds of kilobytes each.
4. **Reproducible builds.** The Docker build runs `npm ci && npm run build`, so the image always contains bundles matching the lockfile.

`public/uv/uv.config.js` is the exception. It is hand written, tracked in git, and deliberately not in the copy list, so the local override is never overwritten.

`src/index.js` verifies the generated files at startup and exits with a clear message if any are missing:

```text
Missing browser bundles:
  public/uv/uv.bundle.js
  ...
Run `npm run build` first, then start the server again.
```

The check covers `uv/uv.bundle.js`, `uv/uv.sw.js`, `uv/uv.config.js`, `baremux/index.js`, and `epoxy/index.mjs` — one representative from each vendored group plus the hand-written config.

### 8.2 Why `docs/` is committed

GitHub Pages has no build step. Whatever is in `docs/` on `main` is what gets served, so the engine bundles there must be committed. `npm run build:site` refreshes them after a dependency change; forgetting to run it means the live site runs stale engine code against a page that may expect a newer API.

This matters more now that there are three engines. `docs/scram/` is vendored and refreshed by the script, while `docs/scram/sw.js` and everything under `docs/keystone/` are hand written and will never be regenerated — a change to them is only live once it is committed. The same is true of `docs/uv/uv.config.js`, which is not touched by the script either.

## 9. Security posture

Keystone is a public proxy endpoint. Anyone who can reach `/wisp/` can ask the server to fetch arbitrary URLs, and those requests originate from the server's IP. The defaults are set accordingly. This section applies to the Node app; a GitHub Pages deployment has no server of its own and inherits whatever policy the remote Wisp server applies.

### 9.1 Wisp refuses internal addresses

```js
wisp.options.allow_private_ips = false;
wisp.options.allow_loopback_ips = false;
```

Without these, a visitor could use the proxy to reach RFC1918 addresses, `127.0.0.1`, or link-local metadata endpoints from inside your network — effectively turning the proxy into an SSRF pivot into your VCN, your other containers, and cloud instance metadata. Both are disabled.

`allow_direct_ip` is left enabled: connections to a literal public IP are allowed, which some sites need. Private and loopback ranges are still blocked, so a literal IP that falls inside them is rejected by the checks above.

### 9.2 Stream limits

```js
wisp.options.stream_limit_total = Number(process.env.WISP_STREAM_LIMIT ?? 200);
wisp.options.stream_limit_per_host = 50;
```

Each proxied request, subresource, and WebSocket is a stream. The limits bound two failure modes:

- **Total (default 200, `WISP_STREAM_LIMIT`)** — caps how much memory and how many outbound sockets one instance can hold. Without it, a single client opening many tabs could exhaust the process.
- **Per host (50)** — prevents one client from monopolizing the budget against a single destination, and limits the amplification a single target can cause.

These are deliberately modest. Raise the total if you have few users and heavy pages; the per-host cap is fixed in code.

### 9.3 Real client IP handling

```js
const trustedProxies = (process.env.TRUSTED_PROXIES ?? "127.0.0.1,::1")...;
wisp.options.parse_real_ip = true;
wisp.options.parse_real_ip_from = trustedProxies;
```

`X-Forwarded-For` is trivially spoofable. If the server trusted it from anyone, a client could forge an address and sidestep per-client accounting. Trust is restricted to a configured peer list, defaulting to loopback. Only those peers may set the header used for real-IP parsing.

Behind the bundled Caddy container, the connecting peer is the `caddy` service address rather than loopback. Set `TRUSTED_PROXIES` to that address if you want forwarded IPs honored in that topology.

### 9.4 HTTP surface

The Express app is intentionally thin:

- `x-powered-by` is disabled, so the framework and version are not advertised.
- `X-Content-Type-Options: nosniff` is set on every response.
- `Referrer-Policy: no-referrer` is set on every response.
- Unknown routes return `public/404.html` with status 404.
- Static caching is split: HTML is `no-cache` (the shell must not go stale), while `/uv/`, `/baremux/`, and `/epoxy/` are `public, max-age=86400` (versioned vendor assets).
- `/healthz` returns `{ok, uptime}` and nothing else — no version, no dependency detail.

Caddy adds TLS and a year-long HSTS header, and strips the `Server` header.

### 9.5 Transport and process hardening

- Epoxy encrypts the browser-to-server stream, so an observer between the client and Keystone sees ciphertext rather than the proxied URLs. This holds for the Pages site too: the encrypted hop runs from the browser to whichever Wisp server the page points at.
- The container runs as the unprivileged `node` user, not root, with only `public/`, `src/`, `node_modules/`, and `package.json` copied into the runtime stage.
- The non-Docker systemd unit (`deploy/keystone.service`) applies `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `ProtectKernelTunables`, `ProtectControlGroups`, and restricts address families to `AF_INET`, `AF_INET6`, and `AF_UNIX`. It binds `HOST=127.0.0.1` so only the local reverse proxy can reach it.
- SIGINT and SIGTERM trigger a graceful close with a 5-second ceiling, so open proxy streams cannot block a restart indefinitely.

### 9.6 What is not protected

- **No authentication.** Anyone who finds the URL can use the proxy. If you need access control, put it in front — Cloudflare Access, an nginx `auth_basic`, a VPN, or an IP allowlist in the VCN.
- **No per-client rate limiting.** Stream limits are global and per-host, not per IP. A determined client can consume the whole budget.
- **No content filtering.** Keystone does not block categories of sites.
- **Your IP is the one sites see.** Abuse complaints arrive at your hosting provider and your account.

The operator is responsible for what the instance is used for.

## 10. Server lifecycle

```text
startup
  |- verify browser bundles exist          -> exit 1 with a list if not
  |- configure Wisp options
  |- build Express app (headers, /healthz, static, 404)
  |- attach the upgrade listener for /wisp/
  +- listen on HOST:PORT                   (default 0.0.0.0:8080)

shutdown (SIGINT / SIGTERM)
  |- stop accepting connections
  +- force exit after 5s if streams are still open
```

The Docker image has a `HEALTHCHECK` that fetches `/healthz` every 30 seconds, and `docker-compose.yml` sets `restart: unless-stopped` on both services, so a crashed app container is restarted and Caddy reconnects to it.

The Pages site has no lifecycle. It is files on a CDN.

## 12. Why there are no blur filters

The page deliberately uses **zero** `backdrop-filter` declarations and no `filter: blur()` on animated elements. This is a performance constraint, not a style preference, and it is easy to undo by accident.

The original design stacked 12 `backdrop-filter` surfaces (the badge, the search bar, six chips, three feature cards, the drawer scrim) on top of three background orbs, each of which ran `filter: blur(100px)` plus an infinite `drift` animation. Every backdrop-filter has to re-sample the pixels behind it, and those pixels were changing every frame because a blurred, animating surface sat underneath. The result was continuous full-page recomposition.

Measured with software rasterisation in headless Edge (`--disable-gpu-compositing`), which is the only way to see this cost, since a GPU and the 75 fps headless cap both hide it:

| | Before | After |
|---|---|---|
| Frame rate | 17.3 fps | 60 fps |
| p95 frame time | 83.2 ms | 16.7 ms |
| Dropped frames | 100% | 0% |

The orbs are now multi-stop `radial-gradient`s at a larger size, which look the same at a glance and cost nothing to composite. The drawer scrim is more opaque (`rgba(3, 4, 9, 0.68)`) to make up for the missing blur.

If a frosted-glass surface is ever added back, expect the frame rate to fall immediately on integrated graphics, and re-measure with `--disable-gpu-compositing` rather than trusting an fps counter that is capped at the display refresh rate.
